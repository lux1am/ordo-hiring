# Отбор кандидатов — анкета с автоскорингом

Публичная форма: кандидат заполняет анкету, ответы с телеметрией попадают в
Google Sheets, дальше автоматика проверяет их и выставляет баллы через
Anthropic API.

Вторая половина проекта — учёт того, откуда кандидаты приходят. Ссылка
раздаётся с меткой размещения, метка едет вместе с ответами, и в книге сама
собирается сводка: какой канал дал откликов, какой пуст, какой выдохся. Раз
в неделю по этим же цифрам уходит отчёт в Телеграм — см. «Учёт размещений» и
«Еженедельный отчёт».

Форму можно поднять двумя способами — на **Google Apps Script** или на
**FastAPI/Render**. Скоринг в обоих случаях один и тот же, различается только
приём анкеты. Выбор описан ниже. Отдельно есть **статическая страница для
своего домена** — она не третий способ приёма, а другая витрина для первого:
[dist/README.md](dist/README.md).

## Два варианта деплоя

|  | Apps Script | FastAPI на Render |
|---|---|---|
| Форму отдаёт | `doGet` | `GET /` |
| Анкету пишет | `doPost` → `SpreadsheetApp` | `POST /submit` → gspread |
| Доступ к таблице | скрипт привязан к ней | сервисный аккаунт |
| Нужен `GOOGLE_CREDENTIALS_JSON` | нет | да |
| Холодный старт | нет | есть на Free-плане |
| Замок аллокации строки | `LockService`, уровень проекта | память процесса, один воркер |
| Лимит отправок по IP | **нет**, адрес недоступен | есть |
| Чем запускается скоринг | `process_new.py` в GitHub Actions, раз в 10 минут | `BackgroundTasks`, сразу |

Заливается через `clasp`: `npm run push` и `npm run deploy` — команды и
подводные камни в [apps-script/README.md](apps-script/README.md), раздел
«Деплой через clasp».

**Apps Script проще и надёжнее для самой формы**: нет сервисного аккаунта, нет
засыпания, блокировка строки работает на уровне проекта, а не процесса.
Расплата — скоринг приходится запускать отдельно (GitHub Actions, раз в
10 минут) и нет ограничения частоты отправок. Установка:
[apps-script/README.md](apps-script/README.md).

**FastAPI нужен, если хочется всё в одном процессе**: анкета обрабатывается
сразу после отправки, лимит по IP работает. Установка — разделы «Деплой на
Render» и «Первый прогон» ниже.

Код обоих вариантов лежит в репозитории и покрыт тестами. При деплое на
Apps Script модули `app/main.py` и `app/ratelimit.py` не используются — они
помечены об этом в docstring. `templates/form.html` используется всегда: это
источник разметки, CSS и JS телеметрии для всех вариантов.

### Своя ссылка вместо `script.google.com`

Адрес веб-приложения Apps Script кандидату показывать необязательно.
`npm run build` собирает из того же `templates/form.html` самодостаточную
страницу `dist/index.html` — с подставленными при сборке вопросами, без
единого внешнего запроса. Она живёт на своём домене, а анкету отправляет
запросом в то же веб-приложение и показывает ответ на месте, без
перезагрузки. Что для этого должно быть настроено и почему запрос уходит с
`Content-Type: text/plain` — в [dist/README.md](dist/README.md).

Домен — **hr.aiordo.ru**, публикация автоматическая: при пуше в `main`
workflow [pages.yml](.github/workflows/pages.yml) пересобирает страницу и
выкладывает `dist/` на GitHub Pages. Один раз это нужно включить:
**Settings → Pages → Source: GitHub Actions** (не «Deploy from a branch») —
без этого прогон падает на `actions/configure-pages`. Домен хранится в
`dist/CNAME`, и файл этот **генерируется сборкой**: Pages выкладывает
артефакт целиком, поэтому положенный руками CNAME пропал бы при первом же
деплое вместе с доменом. Остальное — DNS, сертификат, ручной запуск — в
[dist/README.md](dist/README.md).

## Что происходит с анкетой

1. **Форма** (`GET /`, `doGet` или статическая `dist/index.html`) — из
   `questions.json`: 6 стоп-вопросов с вариантами ответа, 5 вопросов о
   мотивации и ожиданиях и 5 открытых. У третьего стоп-вопроса есть
   уточнение — часовой пояс; отдельной колонки под него нет, оно
   приписывается к ячейке своего вопроса. Вопросы о мотивации баллов не
   дают: из них получаются флаги. Открытые вопросы — короткие задания;
   у третьего жёсткий предел в 70 знаков, и счётчик там показывает
   остаток. На каждую textarea навешена телеметрия: доля вставленных
   символов, скорость набора, количество Backspace, уходы со вкладки, общее
   время. Всё уезжает скрытым полем. Сбор раскрыт кандидату рядом с
   согласием на обработку данных — там же сказано, что на оценку эти
   параметры не влияют. Там же страница читает из адреса параметр `src` —
   метку размещения — и кладёт её в скрытое поле: нет параметра, нет метки,
   анкета всё равно принимается.
2. **Приём** (`POST /submit` или `doPost`) — валидация, проверка на бота и
   дубль, запись строки в лист «Данные», страница «спасибо». Метка чистится
   ещё раз на приёме и ложится в `BC`: поле скрытое, и присланному в нём
   верить нельзя. `doPost`
   принимает и обычную отправку формы, и JSON-запрос со статической
   страницы: проверки общие, различается только ответ — HTML или JSON.
3. **Обработка** — идёт от номера строки. На FastAPI запускается сразу через
   `BackgroundTasks`, на Apps Script — скриптом `process_new.py` по
   расписанию:
   - любой непроходной вариант в стоп-вопросах → вердикт `C`, **модель не
     вызывается**; проходные наборы заданы в `checks.STOP_PASS`;
   - скорер выставляет баллы 0–3 за все пять вопросов с обязательной
     цитатой;
   - флаги вопросов о мотивации вычитываются из `AS` — они записаны туда
     ещё при сабмите;
   - вердикт пишется обратно, статус `done`.

## Раскладка таблицы

Лист **«Данные»**, шапка в строке 1, данные со строки 2. 55 колонок, A…BC.
Порядок задан в [HEADERS.py](HEADERS.py) — это единственный источник истины,
на старте приложение сверяет с ним шапку листа и жалуется в лог при
расхождении.

| Диапазон | Колонки | Что | Кто пишет |
|---|---|---|---|
| `A`–`AH` | 1–34 | id, дата, анкета, стоп-вопросы, ответы, телеметрия | `POST /submit` |
| `AI`–`AM` | 35–39 | `score_q1`…`score_q5` | обработчик |
| **`AN`** | 40 | `total_score` | **никто — формула в таблице** |
| `AO`–`AZ` | 41–52 | `ai_style` … `flags_ru` | обработчик, **частично `/submit`** |
| `BA`–`BB` | 53–54 | `manual_note`, `outcome` | **никто — заполняете вы** |
| `BC` | 55 | `source` — метка размещения | `POST /submit` |

Метка (`BC`) дописана в конец и пишется отдельной ячейкой, а не внутри
анкетной зоны: на границы `A`–`AH` опираются и формула в `AN`, и адреса в
Apps Script, и сдвиг зоны переложил бы баллы в чужие колонки. Откуда метка
берётся — в разделе «Учёт размещений».

Всё пишется с `value_input_option="RAW"`. Колонка `AN` не входит ни в один
диапазон записи: там стоит `=IF(A{row}="","",SUM(AI{row}:AM{row}))`, и сумма
считается таблицей сама. Единственное место, где код использует
`USER_ENTERED` — дозапись этой же формулы начиная с 251-й строки (см. «Лимит
строк»).

### Зона `AO`–`AZ` пишется дважды

Диапазоны не образуют трёх непересекающихся сегментов, как могло бы
показаться по таблице выше. Три ячейки внутри `AO`–`AZ` заполняются уже при
сабмите:

- `AS` (`flags`) — флаги телеметрии и вопросов о мотивации. Считать их при
  обработке нельзя: `is_mobile` и длительность ухода со вкладки в таблицу не
  попадают, отдельных колонок под них нет, и после перезапуска процесса
  восстановить их было бы неоткуда.
- `AP` (`ai_markers`) — ответы на вопросы о мотивации. Отдельной колонки под
  них в раскладке нет, поэтому они делят ячейку с признаками машинного
  текста: там лежит `{"markers": [...], "profile": {...}}`, где `markers`
  пишет обработчик, а `profile` — форма. Сборка и разбор — `pack_markers` и
  `unpack_markers` в [app/profile.py](app/profile.py).
- `AU` (`status`) — начальный `new`.

Обработчик перезаписывает всю зону `AO`–`AZ` целиком, поэтому **он обязан
вычитать `AS` и `AP` перед записью и слить их содержимое со своим** — иначе
`MOBILE`, `PASTED`, флаги мотивации и сами ответы кандидата, записанные при
сабмите, были бы затёрты. Это делают `sheets.read_flags(row)` и
`sheets.read_profile(row)` в начале обработки; поведение закреплено тестами
`test_telemetry_flags_survive_processor_write` и
`test_profile_survives_the_result_write`, которые гоняют полный путь
анкеты — сабмит, фоновая обработка, проверка итоговой строки.

При одном воркере (как настроено в `render.yaml`) две записи в одну зону
разнесены по времени и конфликтовать не могут: обработка стартует только
после того, как `/submit` записал строку. При нескольких воркерах это
перестало бы быть верным — см. «Ограничения».

## Подготовка Google Sheets

> Шаги 1–3 нужны **только для варианта с FastAPI**. При деплое на Apps Script
> сервисный аккаунт не заводится: скрипт привязан к таблице и работает от
> имени владельца. Там достаточно шага 4.

1. В [Google Cloud Console](https://console.cloud.google.com/) создайте
   проект и включите **Google Sheets API**.
2. Создайте **сервисный аккаунт**, в разделе «Ключи» добавьте ключ формата
   JSON и скачайте его.
3. Откройте вашу таблицу и дайте почте сервисного аккаунта
   (`...@...iam.gserviceaccount.com`) доступ **«Редактор»**. Без этого шага
   будет ошибка 403 — сервисный аккаунт не видит таблицу автоматически.
4. Запишите шапку листа «Данные» из `HEADERS.py` и убедитесь, что в `AN`
   стоит формула на нужное число строк:

   ```bash
   python3 apply_headers.py
   ```

Содержимое файла ключа целиком кладётся в переменную
`GOOGLE_CREDENTIALS_JSON` — одной строкой, без файла на диске:

```bash
GOOGLE_CREDENTIALS_JSON=$(cat service-account.json | tr -d '\n')
```

## Смена схемы анкеты

Раздел про разовую операцию. **В обычной работе `archive_old.py` и
`apply_headers.py` не нужны** — они запускаются один раз, когда меняется
состав или смысл колонок: другие стоп-вопросы, другие имена в `HEADERS.py`,
другой набор полей формы. Третий скрипт раздела, `sync_questions.py`,
наоборот, нужен при каждой правке формулировок.

Старые строки нельзя оставить под новой шапкой: колонка сменит имя, а данные
под ней останутся прежними, и `stop_2_chasy` начнёт показывать ответ про
комиссию. Удалить их тоже нельзя — это анкеты живых людей. Поэтому они
уезжают целиком в отдельный лист, вместе со своей шапкой.

```bash
python3 archive_old.py     # 1. увезти старые строки в «Архив (старая анкета)»
python3 apply_headers.py   # 2. записать новую шапку и пересобрать карточку
```

**Порядок обязателен**, и `apply_headers.py` его сторожит: пока в «Данных»
есть строки, он отказывается менять шапку и отсылает к `archive_old.py`.
Обойти проверку можно флагом `--force` — тогда за смысл данных отвечаете вы.

Одно исключение — **колонка, дописанная в конец шапки**: её скрипт пишет и
при непустом листе, без `--force`. Ни одно прежнее имя при этом не
переезжает, и анкеты под ними сохраняют смысл; архивировать живых людей
ради новой колонки незачем. Именно так в лист приехала метка размещения
(`BC`): на боевой таблице достаточно одного `python3 apply_headers.py`.
У обоих скриптов есть `--dry-run`: показать, что будет сделано, ничего не
меняя.

**Что делает `archive_old.py`.** Создаёт лист «Архив (старая анкета)»,
копирует туда шапку прежней раскладки и все строки с данными, помечает лист
скрытым, после чего очищает «Данные» — остаётся шапка и формулы в `AN`.
Формула не трогается намеренно: она размечена на 300 строк вперёд и к данным
отношения не имеет.

Скрипт идемпотентный. Строки узнаются по `id` из колонки `A`, поэтому
повторный запуск ничего не дублирует, а прогон, оборвавшийся между переносом
и очисткой, при следующем запуске дописывает только остаток и доводит дело до
конца. Лист «Архив» переиспользуется, если уже создан. Строку без `id` —
такое бывает после ручной правки — скрипт узнаёт по содержимому целиком:
потерять её нельзя, задвоить тоже.

**Что делает `apply_headers.py`.** Читает `HEADERS.py` и записывает строку 1
листа «Данные», затем перечитывает её и сверяет: расхождение шапки означает,
что баллы попадут не в те ячейки, и узнать об этом лучше сразу. Он же
годится для первой настройки листа — на пустой таблице ему нечего беречь.
В конце он вызывает `sync_questions.py` — карточка пересобирается вместе с
шапкой. Сбой карточки прогон не проваливает: шапка к этому моменту записана
и проверена.

**Что делает `sync_questions.py`.** Собирает лист «Карточка» — одну анкету
целиком, для разговора с кандидатом по телефону. «Данные» для этого не
годятся: 55 колонок кодами, JSON в ячейках, ответ и балл за один вопрос в
разных концах строки. Карточка разворачивает анкету вертикально:

- сверху ячейка с выпадающим списком фамилий (источник — колонка `fio`), а
  рядом решение, уровень, баллы и телеграм;
- **УСЛОВИЯ** — шесть стоп-вопросов с ответом и отметкой ✓/✗ по
  `checks.STOP_PASS`;
- **МОТИВАЦИЯ И ОЖИДАНИЯ** — пять вопросов-флагов с ответом из `ai_markers`
  и названием сработавшего флага по-русски;
- **ОТВЕТЫ** — пять открытых вопросов целиком, с баллом «2 из 3»;
- **ВОПРОСЫ К СКРИНИНГУ** — все строки из `screening_questions` (три от
  модели плюс вопрос от телеметрии, если он есть) и строка «Что смущает» из
  `flags_ru`.

Всё, кроме формулировок вопросов, подтягивается формулами по фамилии из
`A1`: смена фамилии в списке мгновенно перестраивает карточку, запускать
скрипт для этого не нужно. Формулировки берутся из `questions.json` при
сборке и ложатся текстом — они меняются со схемой анкеты, а не с кандидатом.
Он же собирает четыре листа учёта размещений (`placements.py`, раздел
«Учёт размещений») и приводит в порядок видимость: «Данные» и «Архив
(старая анкета)» прячет, «Кандидаты», «Карточка», «Каналы», «Размещения»,
«Личные касания», «Эффективность» и «Как читать» показывает.

Скрипт идемпотентный: карточка собирается заново поверх прежней, а не
дополняется, и выбранная в `A1` фамилия при пересборке сохраняется. В листах
учёта размещений переписываются только шапка и колонки с формулами —
заполненное руками остаётся на месте.

**О печати.** Sheets API не умеет задавать ориентацию, область печати и
масштаб — среди его запросов нет ни одного про печать. Скрипт делает, что
может: ужимает лист ровно до карточки (тогда «Текущий лист» в диалоге печати
и есть область печати) и печатает в конце прогона ссылку на выгрузку в PDF,
где книжная ориентация и вписывание в одну страницу заданы параметрами.

В отличие от двух предыдущих, этот скрипт нужен и в обычной работе — всякий
раз, когда правились формулировки вопросов или слетела видимость листов. Его
`--dry-run` печатает карточку в терминал и в книгу не ходит, поэтому доступа
к таблице не требует вовсе.

Всем троим нужны только `GOOGLE_CREDENTIALS_JSON` и `SHEET_ID`; ключ
Anthropic не требуется. Все зелены на тестах с листом в памяти
([tests/test_migration.py](tests/test_migration.py),
[tests/test_sync_questions.py](tests/test_sync_questions.py),
[tests/test_placements.py](tests/test_placements.py)) — включая повторный
запуск и оборванный прогон.

## Учёт размещений

Отбор начинается раньше анкеты: вакансию нужно где-то разместить. Четыре
листа книги отвечают на один вопрос — что из этого работает. Собирает их
`sync_questions.py` (код — [placements.py](placements.py)), заполняет Ника
руками, считает всё остальное таблица формулами.

### Метку не вводит руками никто

Это главное правило раздела. Ссылка на анкету раздаётся с меткой, и метку
выдаёт таблица:

| Метка | Откуда | Что значит |
|---|---|---|
| `p002` | номер строки листа «Размещения» | один пост в одном канале |
| `lk_16_10` | дата в листе «Личные касания» | все сообщения в личку за день |

Рядом с меткой стоит готовая ссылка — `hr.aiordo.ru?src=p002`. Её копируют
целиком и вставляют в пост или в сообщение. Одна опечатка в метке означала
бы отклики, приписанные не тому каналу, и неверную сводку, по которой потом
принимают решения, — поэтому вводить метку руками негде.

Значение приходит из адресной строки, то есть от кого угодно, и чистится в
трёх местах одинаково: латиница, цифры, подчёркивание и дефис, нижний
регистр, не длиннее сорока знаков. Чистка живёт в
[app/source.py](app/source.py), в общем JS формы и в `Code.gs`; совпадение
трёх реализаций на одних данных закреплено тестом
[tests/test_source.py](tests/test_source.py) — разойдясь, они дали бы разные
метки в зависимости от того, через какую форму пришёл кандидат.

**Строки добавляйте вниз.** Вставленная между заполненными строка сдвигает
номера, а с ними и метки: ссылка, уже ушедшая в пост, начнёт считаться
другому каналу. Предупреждение об этом стоит примечанием к шапке.

### Четыре листа

**«Каналы»** — справочник площадок: название, ссылка, тип. Заполняется один
раз на канал. Название отсюда выбирается в «Размещениях», поэтому
переименование канала задним числом прежние размещения не переименует.

**«Размещения»** — строка на пост: дата, канал из выпадающего списка,
готовая ссылка и справочная колонка «Откликов». Канал именно выбирается, а
не вписывается, и проверка списка строгая: «Авито» и «авито» стали бы двумя
разными каналами, и отдача каждого оказалась бы вдвое меньше настоящей.

**«Личные касания»** — строка на день: дата, сколько сообщений отправлено,
метка дня, ссылка и «Откликов». Метка собирается из даты формулой, поэтому
дату нужно вводить датой, а не текстом.

**«Эффективность»** — сводка, целиком формульная. Это один массив в `A2`, а
не строка на строку: иначе её пришлось бы пересобирать скриптом после
каждого размещения, и между запусками она показывала бы устаревшие числа.
Четыре блока сверху вниз:

1. **по размещению** — дата, канал, откликов, из них A, B и C, средний балл
   и сколько отсеялось на стоп-вопросах. Сортировка по дате, новые сверху;
2. **по каналу** — сколько раз размещались, сколько откликов всего и отдача
   первого размещения против последнего. Выдохшийся канал виден именно
   здесь: число размещений растёт, а последнее из них приносит меньше
   первого;
3. **личные касания** — сколько отправлено и сколько откликов пришло из
   личек. Метка `lk_` чужой не считается — размещения у неё нет по
   определению;
4. **чужие метки и отклики без метки** — метка, которой не соответствует ни
   одно размещение (удалённая строка, правленая руками ссылка), и отклики,
   пришедшие по ссылке без `?src=`.

Строка с нулём откликов серая, строка, где есть хотя бы один кандидат
уровня A, — зелёная. Правила смотрят на числа, а не на текст, поэтому
подписи блоков не красятся.

Средний балл считается по тем откликам, которые до баллов дошли.
Отсеявшиеся на стоп-вопросах не оцениваются вовсе, и держать их в
знаменателе значит занижать отдачу канала тем сильнее, чем честнее он
отобрал людей.

## Еженедельный отчёт

Понедельник, 09:00 МСК: [weekly_report.py](weekly_report.py) считает
прошедшую полную неделю и отправляет отчёт в Телеграм. Запускает его
[.github/workflows/report.yml](.github/workflows/report.yml) — расписание
плюс ручной прогон кнопкой.

```bash
python3 weekly_report.py             # посчитать, собрать, отправить
python3 weekly_report.py --dry-run   # напечатать в терминал, не отправлять
python3 weekly_report.py --no-model  # только цифры, без обращения к модели
```

**Цифры считает код, формулирует модель.** Весь подсчёт — в
[app/report.py](app/report.py), чистыми функциями над прочитанными листами.
Модель (`claude-sonnet-4-6`, промпт — [prompts/report.md](prompts/report.md))
не получает ни одной сырой строки таблицы: только готовый блок чисел.
Поэтому ошибиться в числе она не может — числа стоят в сообщении **выше** её
текста и взяты из кода. Её работа — два коротких раздела: что Ника может
изменить и что относится к вакансии и офферу, а не к её работе. Отвечает
она объектом JSON с двумя полями, заголовки разделов ставит код.

Что считается за неделю, с дельтой к предыдущей: размещения, отклики из
каналов и откликов на размещение; отправленные личные касания, отклики из
личек и конверсия по ним; распределение A/B/C, средний балл, сколько
отсеялось на стоп-вопросах и по каким причинам; дни без единого отклика;
каналы без отдачи и каналы с падающей отдачей; отклики без метки и с чужой
меткой.

**Источники не смешиваются.** Двадцать постов и двадцать сообщений в личку —
разная работа с разной конверсией, и смысл недели в том, какая из них
сработала. Поэтому каналы и личные касания считаются отдельно, у каждого
своя конверсия, а сумма четырёх источников — каналы, личеки, без метки,
чужая метка — всегда равна числу откликов за неделю.

**План.** Дневной: 20 размещений и 20 личных касаний — `PLAN_PLACEMENTS_DAY`
и `PLAN_OUTREACH_DAY` в [app/config.py](app/config.py). Недельный считается
умножением на число рабочих дней в периоде, то есть 100 и 100 за полную
неделю; в отчёте это строка «план / факт / отклонение». Плана по откликам
нет — их число зависит от площадки, а не от усилий; впишете
`PLAN_RESPONSES_WEEK` — строка появится и по ним, больше ничего править не
нужно.

### Как выглядит сообщение

```
<b>Подбор · 13–19 октября</b>

Размещений   14 / 100 ↓6
Личных       62 / 100
Откликов     23 ↑5  (каналы 17 · личеки 6)

A 1 · B 4 · C 18 · средний балл 6,2
Отсев на условиях: 11

Пусто: Работа в продажах, HR чат МСК
Тишина: 14, 15 окт

<b>Нике</b>
Две коротких фразы.

<b>По вакансии</b>
Две коротких фразы.
```

Цифры лежат в `<pre>`-блоке: колонки держатся пробелами, и только так они
не плывут на телефоне. Разметка — HTML (`parse_mode=HTML`), потому что
таблицы Телеграм не рендерит ни в HTML, ни в Markdown; всё, что приходит
извне — названия каналов, текст модели, — экранируется, иначе одна угловая
скобка в названии канала вернула бы ошибку 400.

Дельта показывается только там, где она есть, и одним знаком: `↓6`. Ноль
дельтой не считается — `↑0` в сводке это шум. Строки «Пусто» и «Тишина»
печатаются, только если есть что сказать.

**Потолок сообщения — 1500 знаков**, при пределе Телеграма в 4096: отчёт
читают с телефона в понедельник утром. Соблюдается он за счёт выводов, а не
цифр — у каждого раздела свой предел в 300 знаков, и вышедший за него текст
обрезается по слову. Цифры не режутся никогда: из-за них отчёт и читают.

**Отчёт уходит всегда.** Нет откликов — уходит с явной строкой «Откликов
нет»: пустая неделя это тоже результат. Не ответила модель — уходит один
блок цифр и строка о том, что выводов нет: цифры важнее формулировок. Нет
листа «Размещения» — уходит с нулями и жалобой в лог. Сбой отправки одному
получателю не отменяет отправку остальным; код возврата `1` будет только
если отчёт не получил никто.

Нужны два секрета: `TELEGRAM_BOT_TOKEN` (даёт `@BotFather`) и
`TELEGRAM_CHAT_IDS` — получатели через запятую, текст всем одинаковый.
Добавить человека в рассылку — правка секрета, а не кода.

Получатель записывается как `111111111` (личка), `-1001234567890` (группа)
или `-1004367079334:12` — супергруппа и номер темы в ней: тогда отчёт
падает в свою ветку, а не в общий поток.

**Неверный номер темы отчёт не теряет**, и страхует это дважды. Номер,
который не разобрался, отбрасывается при чтении секрета. А номер, который
разобрался, но Телеграм его не принял — тема удалена, закрыта или
перенумерована, — виден только в момент отправки: на такой отказ (400 со
словом `thread` или `topic` в описании) код повторяет отправку тому же
чату уже без темы и пишет в лог, что поправить. Отчёт в общем потоке хуже
отчёта в своей ветке, но несравнимо лучше отчёта, которого нет, — тем
более что обнаружилось бы это в понедельник утром, когда править некому.
Прочие отказы — «чата нет», «бот не в группе» — темой не лечатся и не
повторяются.

## Локальный запуск

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env          # заполните ANTHROPIC_API_KEY, GOOGLE_CREDENTIALS_JSON, SHEET_ID
set -a && source .env && set +a
.venv/bin/uvicorn app.main:app --reload
```

Форма — на `http://127.0.0.1:8000/`, состояние — на `/health`.

## Деплой на Render

1. Залейте репозиторий на GitHub.
2. В Render: **New → Blueprint**, укажите репозиторий. Render прочитает
   [render.yaml](render.yaml) и создаст веб-сервис.
3. В настройках сервиса задайте три секрета (в `render.yaml` они помечены
   `sync: false`, то есть в репозиторий не попадают):
   - `ANTHROPIC_API_KEY`
   - `GOOGLE_CREDENTIALS_JSON` — весь JSON одной строкой
   - `SHEET_ID` — из адреса таблицы, часть между `/d/` и `/edit`
4. Задеплойте и откройте `/health`: там должно быть `{"status":"ok"}`.
   `misconfigured` со списком `missing_env` означает, что секрет не задан.

Логи пишутся в stdout и видны во вкладке Logs. Каждая принятая анкета
логируется целиком одной JSON-строкой **до** записи в таблицу: диск на
Render не переживает рестарт, а логи остаются, и при сбое Google API анкету
можно восстановить руками.

### Про Free-план

На бесплатном плане сервис засыпает после 15 минут без запросов, и первый
запрос после сна идёт около полминуты. Для формы это терпимо. Что важнее:
засыпание убивает фоновую обработку на полпути — от этого защищает
восстановление зависших строк, описанное ниже.

## Публикация формы: GitHub Actions

Перед первым прогоном включите Pages: **Settings → Pages → Source: GitHub

## Запуск обработки: GitHub Actions

`doPost` в Apps Script пишет строку со статусом `new` и на этом
останавливается — фоновых задач там нет. Скоринг запускает
[.github/workflows/worker.yml](.github/workflows/worker.yml): каждые
10 минут поднимает `ubuntu-latest`, ставит зависимости и выполняет
`process_new.py`.

Записав строку, `doPost` вдобавок просит GitHub запустить тот же workflow
немедленно (`workflow_dispatch` через API). Расписание из-за этого не
убирается: вызов может не пройти — истёк токен, не ответил GitHub, — и тогда
анкету заберёт ближайший прогон по расписанию. Токен лежит в свойствах
скрипта, как его туда положить — в
[apps-script/README.md](apps-script/README.md), раздел «Токен GitHub в
свойствах скрипта».

### Секреты

**Settings → Secrets and variables → Actions → New repository secret.**
Первые три — ровно те же значения, что и для Render; последние два нужны
только еженедельному отчёту:

| Имя | Значение |
|---|---|
| `ANTHROPIC_API_KEY` | ключ из [console.anthropic.com](https://console.anthropic.com/settings/keys) |
| `GOOGLE_CREDENTIALS_JSON` | содержимое файла ключа сервисного аккаунта **целиком** |
| `SHEET_ID` | часть адреса таблицы между `/d/` и `/edit` |
| `TELEGRAM_BOT_TOKEN` | токен бота от `@BotFather` |
| `TELEGRAM_CHAT_IDS` | получатели отчёта через запятую; у групп ID с минусом, тема супергруппы — через двоеточие: `-1004367079334:12` |

`GOOGLE_CREDENTIALS_JSON` вставляйте как есть, вместе с переносами строк
внутри — поле секрета многострочное, и `process_new.py` разбирает такой JSON
без правок. Экранировать `\n` вручную не нужно.

> Даже при форме на Apps Script сервисный аккаунт нужен: скрипт в таблице
> пишет от вашего имени, а обработчик приходит снаружи, из Actions, и ему
> требуется собственный доступ. Заведите его по шагам 1–3 раздела
> «Подготовка Google Sheets».

Необязательно, если лист или часовой пояс отличаются от значений по
умолчанию, — **Variables** (соседняя вкладка, не Secrets): `WORKSHEET_NAME`
и `TZ_OFFSET_HOURS`.

### Расписание задерживается — это нормально

На бесплатном тарифе `schedule` не гарантирует точность: при общей нагрузке
на GitHub запуск сдвигается на несколько минут, а в пиковые часы задержка
доходит до десятков минут. Иногда отдельный запуск пропускается совсем.

Для отбора кандидатов это несущественно — анкета подождёт. Важно другое:
**не считайте расписание таймером.** Ничего не сломается, если прогон
пропущен: строки остаются в `new` и будут подобраны следующим запуском.

Нужна анкета сейчас — **Actions → worker → Run workflow**. Ручной запуск
срабатывает сразу.

Ещё одна особенность бесплатного тарифа: GitHub отключает `schedule` в
репозиториях, где 60 дней не было активности, и присылает об этом письмо.
Включается обратно одним нажатием на странице Actions.

### Два прогона не дерутся за строки

```yaml
concurrency:
  group: worker
  cancel-in-progress: false
```

Если предыдущий прогон ещё идёт, новый ждёт его, а не отменяет. Отмена была
бы хуже пропуска: прерванный прогон оставил бы строки в `processing` на
середине обработки.

Страховка на случай, когда прогон всё же убит — таймаутом в 10 минут или
вручную: каждый следующий запуск начинается с возврата всех `processing` в
`new`. Каждый прогон Actions — новый процесс, поэтому строки в `processing`
по определению остались от прерванного.

### Где смотреть, что происходит

Панели нет, окно наблюдения — страница прогона. Внизу неё, без разворачивания
логов, выводится сводка:

```
СВОДКА ПРОГОНА
  зависших строк возвращено : 1
  строк обработано          : 4
      оценено                       : 3
      в ручную проверку             : 1
```

Она же печатается в лог шага «Обработка анкет».

**Зелёный прогон** — всё штатно. Строки в `manual` ошибкой не считаются: это
рабочий исход, кандидата надо посмотреть руками.

**Красный прогон** означает одно из трёх: не заданы секреты (код возврата 2),
не читается лист, или строка упала с необработанным исключением. В последнем
случае она осталась в `processing` и будет подобрана следующим запуском —
но в лог стоит заглянуть, причина повторится. GitHub пришлёт письмо о
падении сам.

## Первый прогон

Шесть шагов после первого деплоя. Порядок важен: каждый следующий имеет
смысл, только если предыдущий прошёл.

Шаги ниже написаны для варианта с FastAPI. Для Apps Script шаги 1–2
заменяются запуском функции `checkSetup` из редактора
([apps-script/README.md](apps-script/README.md), шаг 4), шаг 5 частично
неприменим — лимита по IP там нет, — а после шага 3 анкету нужно провести
через `process_new.py`. Шаги 3, 4 и 6 совпадают полностью.

**1. `/health` отвечает `ok`.**
Откройте `https://<ваш-сервис>.onrender.com/health`. Ответ
`{"status":"ok","missing_env":[]}` означает, что все три секрета на месте.
Если видите `misconfigured` — в поле `missing_env` перечислено, чего не
хватает; допишите в Environment и передеплойте.

**2. Шапка листа совпала с `HEADERS.py`.**
В логах Render найдите строку при старте:

```
INFO [app.sheets] шапка листа совпадает с HEADERS.py (55 колонок)
```

Если вместо неё `ШАПКА РАСХОДИТСЯ: колонка ... — ожидалось «...», в таблице
«...»` — порядок колонок разъехался, и баллы попадут не в те ячейки.
Останавливайтесь здесь и приводите шапку в соответствие. Ошибка
`APIError: 403` на этом шаге означает, что таблица не расшарена на почту
сервисного аккаунта.

**3. Обычная анкета доходит до `done`.**
Отправьте тестовую анкету, выбрав проходные варианты во всех шести
стоп-вопросах и написав в открытые вопросы осмысленные ответы.
Проверьте строку 2:

- `A`–`AH` заполнены, `created_at` в вашем часовом поясе;
- `AI`–`AM` содержат баллы, **`AN` показывает их сумму** — если `AN` пустая,
  формула в таблице не проставлена;
- `AU` (`status`) равен `done` или `manual`;
- `AW`–`AZ` заполнены по-русски;
- `BA`–`BB` пустые.

**4. Стоп-вопрос отсекает без вызова модели.**
Отправьте вторую анкету с другим телеграмом и одним непроходным вариантом —
например, «10–14» часов в неделю. Ожидается `verdict=C`, `status=done`,
`conditions_ru` вида «Не проходит: ...», а `AI`–`AM` пустые. В логах не должно быть ни строки про скорер — это и есть
подтверждение, что деньги на заведомый отказ не потрачены.

**5. Дубль и лимит отправок работают.**
Отправьте анкету с тем же телеграмом, что в шаге 3, — должна появиться
строка со `status=duplicate` и без вызова модели. Затем отправьте шесть
анкет подряд с одного устройства: шестая должна вернуть страницу с
сообщением о превышении лимита.

**6. Эталонный прогон и калибровка.**
Локально, с боевым ключом:

```bash
.venv/bin/python tests/run_golden.py
```

Смотрите на среднюю ошибку и долю расхождений не больше 1. Если модель
систематически занижает или завышает какой-то вопрос — правьте не код, а
`rubric/qN.md`: добавьте к спорному баллу пример реального ответа. После
правки прогоняйте снова.

После шага 6 очистите тестовые строки. Следующая свободная строка считается
по длине колонки `A`, поэтому очищать нужно **с конца и вместе с колонкой
`A`**: тогда счётчик вернётся назад и строки переиспользуются. Пустая строка
в середине счётчиком не учитывается и просто останется дыркой — это не
ошибка, но и не переиспользование.

## Проверки без обращения к модели

| Флаг | Когда ставится |
|---|---|
| `PASTED` | доля вставки > 30% или скорость выше порога |
| `SUSPICIOUS` | ни одного Backspace при ответе длиннее 400 знаков |
| `TAB_SWITCH` | уход со вкладки дольше 60 секунд, после которого кандидат дописывал ответ |
| `MOBILE` | анкета заполнена с телефона |

Флаги вопросов о мотивации (`checks.profile_flags`) считаются при сабмите и
ложатся в ту же колонку `AS`:

| Флаг | Когда ставится |
|---|---|
| `MOTIVATION_AVOIDANCE` | единственный мотив — «уйти на удалёнку» или «сменить сферу» |
| `INCOME_LOW` | реалистичным считает доход до 50 000 ₽ |
| `INCOME_UNREAL` | реалистичным считает доход выше 150 000 ₽ |
| `STABILITY_FIRST` | стабильность на первом месте в ранжировании |
| `INCOME_NOT_PRIORITY` | доход на третьем или четвёртом месте |
| `UNDERESTIMATE` | план по встречам считает «легко достижимым» |
| `PESSIMIST` | план по встречам считает нереальным |
| `NO_GOALS` | не знает, кем хочет быть через 6–12 месяцев |

Сами ответы хранятся в `AP` (`ai_markers`) JSON-ом — отдельной колонки под
них в раскладке нет. Читать JSON глазами неудобно, поэтому та же информация
дописывается в `AZ` (`flags_ru`) фразой:

```
заполнено с телефона; мотивация: высокий доход без потолка; доход 80–120к;
приоритет: доход, график, рост, стабильность; встречи — достижимо при
усилиях; цель — РОП
```

Собирает её `ru.profile_ru`. Текст из варианта «другое» подставляется вместо
самого слова «Другое» — рекрутёру нужен ответ, а не название пункта.

**Телефоны проверяются мягче.** На мобильных `keydown` по Backspace приходит
нестабильно, а свайп-ввод и автозамена дают скорость, при которой порог для
настольных браузеров срабатывал бы почти на всех. Поэтому на мобильных
`SUSPICIOUS` отключён полностью, а порог скорости поднят с 400 до 700 зн/мин.
Событие `paste` работает везде одинаково, так что `PASTED` не смягчается.

## Баллы и вердикт

Сумма пяти баллов (0–3 каждый) даёт вердикт: **12–15 → A**, **9–11 → B**,
**0–8 → C**.

- `A` понижается до `B` при флагах `STABILITY_FIRST`, `INCOME_UNREAL`,
  `MOTIVATION_AVOIDANCE` или при `ai_style > 70`. Список — в
  `verdict.DOWNGRADE_FLAGS`.
- Остальные флаги мотивации только показываются рекрутёру: сами по себе они
  не отменяют сильных ответов.

**Все пять баллов ставит модель.** Числовых полей, которые раньше считались
кодом, в анкете нет: вакансия не требует опыта продаж, и спрашивать выручку
по месяцам не о чем. Шкалы — в [rubric/q1.md](rubric/q1.md)…[q5.md](rubric/q5.md).

**Телеметрия вердикт не понижает.** `PASTED`, `SUSPICIOUS` и `TAB_SWITCH`
говорят о том, как заполняли анкету, а не о том, что в ней написано:
вставленный текст не доказывает ни слабости кандидата, ни обмана. Вместо
понижения в `screening_questions` добавляется четвёртая строка —
«уточнить ответы голосом — часть текста вставлена». В `flags_ru` флаги
пишутся по-прежнему и видны в таблице.

**Балл выше нуля живёт только при дословной цитате.** Это требование стоит
в системном промпте, но проверяется кодом: цитата ищется в тексте ответа
после нормализации (схлопывание пробелов, нижний регистр, снятие кавычек и
тире), а цитата длиннее 15 слов считается пересказом. Не прошла проверку —
балл обнуляется, причина уходит в `flags_ru`.

### Когда анкета уходит в `manual`

Источник ровно один — **сбой скорера**: невалидный JSON после повтора или
исчерпанные попытки после 429. Баллов в этом случае нет вообще, поэтому
вердикт принудительно `B`, а в `flags_ru` уходит «оценка не выполнена,
проверить вручную» плюс техническая причина. Иначе кандидат получал бы отказ
за битый JSON — то есть за чужую вину. Закреплено тестом
`test_scorer_failure_is_never_a_refusal`.

Колонки при этом не остаются пустыми: `decision_ru` = «Проверить руками»,
`conditions_ru` заполнен всегда.

## Надёжность

**Ретраи Anthropic API.** Три попытки с задержками 2/8/30 секунд. Встроенные ретраи SDK отключены (`max_retries=0`)
намеренно: иначе задержки перемножились бы и разбор волны откликов растянулся
бы на часы. В `manual` анкета уходит только после исчерпания всех попыток.

**Восстановление зависших строк.** Если процесс упал или Render
передеплоился посреди обработки, строка осталась бы в `processing` навсегда.
На старте приложения все `processing` возвращаются в `new` и ставятся в
обработку заново; дальше раз в 5 минут то же делается со строками, висящими
дольше 10 минут. Реестр захваченных строк живёт в памяти процесса, поэтому
после перезапуска все `processing` в таблице по определению осиротевшие.

**Идемпотентность.** Обработка начинается с перевода строки из `new` в
`processing` и не стартует ни при каком другом статусе. Повторная обработка
одной строки невозможна.

**Защита формы.** Скрытое стилями поле-приманка (заполнено → отвечаем
«спасибо», но в таблицу ничего не пишем, чтобы боты не съедали строки);
не больше 5 отправок с одного IP в час; повторная анкета с тем же телеграмом
пишется со статусом `duplicate` и модель не вызывает.

## Ограничения

**Один инстанс — только для варианта с FastAPI.** Номер строки выделяется
так: прочитать длину колонки `A`, записать в следующую. Внутри процесса это
защищено замком, но при нескольких воркерах два одновременных сабмита могут
получить одну строку. Поэтому в `render.yaml` стоит `--workers 1`. Если
будете включать масштабирование, замок придётся переносить в саму таблицу.
В Apps Script этой проблемы нет: `LockService.getScriptLock()` работает на
уровне всего проекта.

**Лимит отправок по IP есть только в FastAPI.** Apps Script не даёт адреса
клиента. Honeypot и проверка дубля по телеграму работают в обоих вариантах.

**`append_row` не используется намеренно.** Формула в `AN` на 300 строк
вперёд делает эти ячейки непустыми для Sheets API, и `append_row` ушёл бы
сразу за размеченный диапазон. Поэтому строка считается по колонке `A`, где
формул нет.

**Лимит строк.** Начиная с 251-й строки код сам дописывает формулу
`total_score` в `AN` — для строк 251–301 это перезапись той же формулы, а
дальше единственный способ не оставить сумму пустой. Так лимит в 300 строк
снимается сам; при выходе за размеченный диапазон в лог пишется
предупреждение.

**`notified` не заполняется.** Колонка оставлена заглушкой под уведомления,
которые добавляются отдельным шагом.

## Тесты

```bash
.venv/bin/python -m pytest tests/ -q
```

Около четырёхсот детерминированных тестов на JSON-фикстурах: раскладка
колонок и зоны записи, флаги телеметрии (включая мобильные послабления и
границы порогов), проходные наборы стоп-вопросов, флаги вопросов о
мотивации, пороги и понижения вердикта, сверка цитат, валидация формы,
идемпотентность конвейера, восстановление зависших строк, сквозной путь
«сабмит → обработка», разовые скрипты смены схемы на листе в памяти, чистка
метки размещения тремя реализациями на одних данных, формулы листов учёта
(каждая функция сверена со списком существующих в Sheets, каждое имя `LET` —
с местом, где оно объявлено), цифры еженедельного отчёта на выдуманных
неделях и его рассылка, в которой один отказавший получатель не отменяет
остальных. Проверки множественного выбора и ранжирования не
сверяются по строкам, а исполняются в node на подставном DOM — там же
сверяются флаги Apps Script с флагами Python на одних данных. Сети не
требуют.

Отдельно — эталонный прогон через реальный API с таблицей расхождений:

```bash
.venv/bin/python tests/run_golden.py                 # все фикстуры
.venv/bin/python tests/run_golden.py 01_strong_a     # выборочно
```

Он печатает по каждой фикстуре эталонный и полученный балл, среднюю ошибку,
долю расхождений не больше 1 и совпадение вердиктов. Из pytest вынесен
намеренно: это настоящие вызовы модели, то есть деньги и минуты. Запускайте
после правки промпта или рубрик.

## Настройка под себя

- **Тексты вопросов и варианты ответов** — [questions.json](questions.json).
  Поля `field` стоп-вопросов должны совпадать с именами колонок в
  `HEADERS.py`. Переименование колонки — правка в двух местах сразу:
  в `HEADERS.py` и в шапке листа руками; расхождение поймает сверка при
  старте.
- **Проходные варианты стоп-вопросов** — `STOP_PASS` в
  [app/checks.py](app/checks.py). Любое значение вне набора даёт `C` без
  вызова модели. Строки сверяются с `questions.json` при импорте модуля:
  опечатка в коротком тире иначе молча отсекала бы всех.
- **Правила флагов мотивации** — `profile_flags` там же. Их копия для
  Apps Script лежит в `Code.gs`, совпадение закреплено тестом
  `test_profile_flags_match_python_on_edges`.
- **Переименование колонки** — правка сразу в двух местах: `HEADERS.py` и
  шапка листа руками. Расхождение поймает сверка при старте (`ensure_header`
  на FastAPI, `checkSetup` в Apps Script) — она пишет в лог, какая колонка
  разъехалась.
- **План на день** — `PLAN_PLACEMENTS_DAY` и `PLAN_OUTREACH_DAY` в
  [app/config.py](app/config.py). Недельный план считается умножением на
  число рабочих дней в периоде; править его отдельно негде и не нужно.
- **Домен формы** — `FORM_DOMAIN` там же. Отсюда его берут и сборка
  `dist/CNAME`, и формула «Ссылка для размещения» в листе «Размещения»:
  домен, записанный в двух местах, однажды разъедется, и ссылка поедет в
  никуда.
- **Сколько строк размечать** — `PLACEMENT_ROWS`, `OUTREACH_ROWS` и
  `CHANNEL_ROWS` в [placements.py](placements.py). Лист при этом только
  растёт: ужать его значило бы стереть заполненное руками.
- **Критерии оценки** — [rubric/q1.md](rubric/q1.md)…[q5.md](rubric/q5.md).
  В каждом файле оставлено место под примеры реальных ответов: добавьте по
  паре примеров к каждому баллу, и разброс оценок заметно сократится.
- **Правила скоринга** — [prompts/system.md](prompts/system.md).
- **Пороги** — переменные окружения, все перечислены в
  [.env.example](.env.example). Менять код для этого не нужно.
